# Changes, worktrees and comparing models

## Reviewing changes

**Changes** (the side panel's row, the title bar's changes chip, a turn's **Review changes**, or Ctrl+Shift+G, ⇧⌘G on a Mac, which closes it too) opens a review pane: the changed files with git's status letter and +/− counts, and each file's diff, unified or split. It refreshes when a turn ends, when you come back to the window, and after the terminal panel goes quiet. In a Git repository it shows what git sees, whoever made the change (Cavvy's tools, Claude Code or Codex, a shell command or you):

- **Uncommitted**, the default: the working tree against the last commit, so staged, unstaged and untracked files that aren't ignored.
- **Branch**: everything since this branch left its base (`feat/x → origin/main`), committed or not. The base starts as the main branch (what `origin/HEAD` points at, else `main` or `master`), and you can pick another from a searchable list of local and remote branches.
- **Commit**: one commit against its parent, a merge against its first parent. It opens on the last commit; the picker beside it lists HEAD's last 100 commits, newest first, searchable by subject, id or author. It reads git's objects only, never the files on disk, and the list is read each time the picker opens.
- **Last turn** and **Turn N**: the difference between a prompt’s start and end snapshots, including shell commands, any provider’s tools, and sub-agent work during that turn. Pick an earlier prompt by its text and time, including after reopening the session. A steered prompt closes the preceding snapshot and starts a new one. The turn’s changed-files card opens that exact turn.
- **Cavvy edits**: only what Cavvy's own edit tools changed in this session. Outside a Git repository it's the only view, and the pane says so.

**Ignore whitespace** (the toolbar's space-bar button, on by default and remembered on this device) treats lines that differ only in whitespace as unchanged, as `git diff -w` does, in every view and in the title bar's and side panel's counts. A file whose changes are all whitespace is still listed, saying so. Turn it off to review indentation or trailing spaces. Committing is unaffected: it commits the files as they are.

Each file's diff keeps three lines of context around its changes. **Show N hidden lines**, in a hunk's header and after the last hunk, puts the lines left out there back; the first click in a file fetches it once, in full, with every line as context, for the view it's in, and nothing is read before that. If the file changed since its diff was listed, the lines stay hidden until it's refreshed. The copy button in a file's header copies its path as listed (relative to the session's folder); Alt-click (⌥-click) copies its full path.

Up to 300 files are listed, with a count of the rest. A new folder with many untracked files (an unignored `node_modules`) is one entry, and so are submodules and repositories inside this one. Symbolic links are diffed as their targets and never followed. Binary, very large and cut diffs say so. Listing and viewing diffs only reads: it never stages, writes the index or runs anything from the repository's config. `git status` and `git diff` would run a repository's clean filters, so Cavvy lists the trees and the index with git and compares the files on disk itself. A file git runs through a filter (Git LFS, say) is settled by the index's record of it, as git does: if it hasn't changed since git last looked it isn't listed, and if it has, it's listed without a diff, since diffing it would mean running the filter.

### Turn snapshots

Turn snapshots are recorded by the shared agent in trusted, saved Git sessions (GUI, terminal, and headless). They cover tracked files and untracked files that are not ignored, preserving the bytes on disk, executable bits, and symlink target text. Ignored untracked files (including an ignored `.env`), files over 10 MB, unreadable/special files, and the contents of submodules or nested repositories are not copied. Skipped files are marked; a capture that exceeds its budget (about 2 seconds at a turn's start, which the model waits on, and 10 at its end, so a turn that changed thousands of files is still read whole) is marked incomplete instead of delaying the model indefinitely. A session's first capture that runs out of time (a big repository on a busy machine) goes on after the turn stops waiting for it, for up to 10 minutes (with many sessions on a busy machine, each one's waits for the others'), and the next turns start from it rather than looking at everything again. A turn is done when its agent is: its closing snapshot is taken just after, and its changes and the Changes badge show once it's in. A next turn sent meanwhile starts once that snapshot is taken, before it's compared with the turn's start. Closing a turn also has a separate 2-second comparison budget, including at a steering boundary. A crash or server stop that cuts a turn off can leave a start without an end. Reopening preserves that start and never invents a closing snapshot from the current files. The card and Review show that the snapshot is incomplete; the card retains any edit-tool diffs available, but shell/backend changes have no exact turn diff without an end. Later prompts start separate snapshots. Changes made by a background task after its turn ended aren't attributed to a turn. Concurrent sessions or other processes in the same repository contribute to each other’s turn diffs; capture is a bounded scan, not an atomic filesystem transaction. The Changes badge counts distinct paths listed by recorded turn diffs plus legacy edit-tool history (omissions with unchanged metadata are not counted), so it may differ from the current Uncommitted count.

A turn's card also names the repository's other worktrees it worked in, each summed up as its branch against the main branch: one that changed, or appeared, while the turn ran, and that the turn reached. Reached means the agent worked in it, or a tool call that isn't read-only named a path in it (a file it wrote, a command's `cd`, `git -C` or file argument). A worktree another session or you changed meanwhile isn't this turn's. Worktrees inside the main checkout's folder are looked at first, then those elsewhere, 16 at most. A turn's start notes only which worktrees there are, and the time; at its end, only the worktrees it reached are looked at: whether their HEAD, branch or index was written since it began, and their files, for any changed since (by ctime, which every write, rename and mode change moves), so many sessions in many worktrees of a large repository don't each read all of them every turn. A tracked file deleted in one counts when its folder changed during the turn.

Storage lives beside file history: `turn-snapshots.jsonl` is a versioned append-only journal of checkpoint ids, prompt labels/times, start/end tree ids and omissions; `turn-snapshots/` contains a reusable private index and private Git objects. Direct raw object hashing/compression is equivalent to [`hash-object --no-filters`](https://git-scm.com/docs/git-hash-object), followed by [`update-index --index-info` and `write-tree`](https://git-scm.com/docs/git-update-index). `git add` is deliberately avoided because it applies [clean/process filters and EOL conversion](https://git-scm.com/docs/gitattributes). Git commands disable fsmonitor, index hooks, split index and lazy fetching; inherited repository environment overrides are cleared before the private index/object paths are applied. No refs, objects, index, stash or hooks in the repository are changed. Folders are 0700 and files 0600. Each session has a 256 MiB quota for compressed private objects (blobs and trees); reaching it stops capture and marks the snapshot incomplete while the turn continues. Objects left by failed or timed-out captures count toward the quota and remain until file-history pruning: removing them safely would require checking references across all retained trees. Unpublished temporary writes are removed when possible. The quota does not cover the journal, private index, or legacy edit-tool copies. A file Git's index has as it is on disk (every stat field the index recorded still matches, it isn't racily clean, and no attribute or `core.autocrlf` makes Git store anything but its bytes) is captured by the blob id the index names, without being read or copied: in a large repository the first capture takes about as long as `git status`, and the store holds only what turns changed. When a turn ends, both versions of every file it changed are copied into the private store from the repository's objects, checked against their ids, so a turn's diff never depends on the repository's objects afterwards: its garbage collection cannot invalidate history. Everything else is stored privately rather than borrowed through alternates. In a big repository (5,000 files or more), a session's first capture asks `git status` what differs from Git's index (without letting it write the index) and edits the tree Git last worked out for the index (its cache-tree, after a checkout or a commit) along those paths, or, with something staged since (no such tree), HEAD's tree along those and the staged paths, refusing if HEAD moved while `git status` ran: about what `git status` itself costs, plus the folder's watch starting first. `git status` runs with every filter Git's config defines (git-lfs's, for one) set to run nothing, no hooks, and, on Git 2.41 or later, attributes read from the empty tree rather than the folder's `.gitattributes` files. Where `git status` can't say plainly what's on disk (a conflict, a submodule, assume-unchanged or skip-worktree entries, intent-to-add, neither a tree worked out for the index nor a commit, more than 2,000 paths), where it can't be kept from running a program (the repository's config includes another file, or the config can't be read plainly), and in a small repository, it compares every file with Git's index here (on several threads in a big repository while the machine has cores to spare) and starts from that tree, or else from a copy of the index, with only what differs from it read (so nothing of the unchanged files is held in memory). A later capture looks only at the paths the folder's watch saw change since (it first writes an empty marker file in the repository's `.git` folder and waits for the watch to report it, which it does after every change made before it, then removes it, and one a stopped process left behind is removed when the watch starts; in a linked worktree or a folder without its own `.git` folder it waits a fixed moment instead, and a watch whose marker isn't reported within 2 seconds is no longer relied on; a new watch is relied on only once the system shows it's reporting changes, a marker reported in a repository and 250 ms elsewhere on a Mac, since a change made before that is never reported), and after a commit at the paths whose entries in the index changed, and edits the last tree along them: in a 100,000-file repository a turn that edited a few files costs about what `git add` of them does. It looks at everything again when it can't tell what changed (an ignore or attributes file or Git's config changed, the index records something new and Git worked out no tree for it, more than 2,000 paths changed, the watch failed), and every 32 captures or 10 minutes. A turn that wrote nothing (only read-only tool calls, its sub-agents' too), and a turn's start right after the last one's end, in a folder whose watch saw no change since the last capture takes that capture again, starting no process and reading no file; without a watch (the system's limit on watched folders reached, say, or a Bun older than 1.4.4 running Cavvy from source: its macOS watch can leave changes out) every capture looks. Missing or damaged private objects are shown as incomplete. Old sessions and non-Git folders retain their previous behavior.

Native backend history is insufficient for this recording: [Claude Code checkpointing](https://code.claude.com/docs/en/agent-sdk/file-checkpointing) excludes Bash and most sub-agent edits, while Codex app-server’s [`thread/revert`](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/src/protocol/v2/thread.rs) changes conversation history rather than restoring local files. The common snapshot record covers all providers, and `/rewind` restores files from it.

### Rewinding files

Rewinding with files restored (`/rewind`, or **Rewind** in the GUI, a prompt's rewind button, with **Code only** or **Restore both**) puts the repository back as it was when the chosen prompt started, using that prompt's turn snapshot. The files are captured again (as a turn's end is), compared with the snapshot's start, and every path that differs is written back from the snapshot's objects (the private store, else the repository's, each checked against its id), deleted where it didn't exist then, or made again where it was deleted since. A rename is both. Bytes, the executable bit and symlink targets are restored as recorded; a file is written beside its place and renamed over it, so a link there is replaced, never followed, and no folder on the way may be a link. Folders a deleted file leaves empty are removed. What snapshots don't cover is left alone: ignored files, files over 10 MB or unreadable (Cavvy's edit-tool copy is used where it has one), and the contents of submodules and repositories inside this one. The whole repository counts, not only the session's folder within it. A file that changes between the dialog showing the list and the restore is left as it is and reported.

The capture taken just before restoring is what **Undo** (the toast's, **Undo last restore** in the Rewind dialog, or `/rewind undo`) puts back: only the files the restore wrote, and each only if it's still as the restore left it. The versions it needs are copied into the session's private store first, and the list of what to put back is saved beside the session's snapshots, so Undo outlasts closing the app or terminal. Undo is offered for the session's last restore only; it doesn't undo a rewound conversation.

Restoring every file is refused, with the reason, when the prompt has no snapshot (an older session, an untrusted folder, a prompt the snapshot timed out on, or history pruned after 30 days), when the snapshot's objects are gone, when the files can't be captured now, and when another session works in the same repository: in the app, a session that's working (or closing); from another process (the terminal, another app), any session it has open there, since whether it's working can't be told. The dialog then offers what Cavvy's own edit tools changed, from their copies, as before. A non-Git folder offers only that, without a reason. Reading the files for the dialog and restoring are the only work this adds, both on your asking; turns record nothing more.

Agent CLI sessions (Claude Code, Codex, OpenCode, Grok Build, Antigravity) can't rewind their own threads, so Cavvy rewinds the conversation itself: a CLI thread that saw past the rewind point is let go, and the next prompt starts a new one with the conversation as kept as context. Their files are restored the same way as for Cavvy's own models. **Code only** restores files to before a prompt without touching the conversation, for every kind of session.

### Committing

In **Uncommitted**, each file has a checkbox, checked by default. Untick files to leave out, then click **Commit…** to review the branch and selection and enter a subject and optional body. The dialog warns on the main branch or a detached HEAD. Committing is disabled while the session works and refused by the server in untrusted folders. It commits the checked files' current contents, including whole renames and deletions, while other files keep their staging and working changes. Repository hooks run and configured commit signing is honored; a hook that stages unchecked files is rejected before the branch moves. Success shows the short hash and subject and refreshes the pane; failures show Git's output. It never pushes or amends. Collapsed untracked folders and nested repositories cannot be checked as one file.

Hooks receive the private index, including `post-commit`; staging done by `post-commit` is discarded so unchecked files keep their staging. Hooks still run with the trusted repository's normal access to its working files. Git commands have a two-minute limit and timed-out hooks are stopped. If a hook times out after the commit was published, Cavvy still reports the successful commit and reconciles the index.

**Generate message** runs only when clicked, using the `smallModel` chosen in Settings, otherwise a small model from the session's provider, or the session's own model if none is available. It receives a redacted, budgeted diff of the selection and recent commit subjects, and puts an editable draft in the box; hovering the button names the model. Claude Code and Codex sessions need `smallModel` set to a model on another provider that supports one-off requests. Generating never commits; you can always write the message yourself.

On the main branch or a detached HEAD, where the dialog warns, **Commit to a new branch** commits there instead: a branch made where HEAD is, which is then checked out; the branch you were on doesn't move, and the files and other staged changes stay as they are. Ticking it asks the same small model for a name from the message's subject (or, without one, the session's title), after your `worktree.branchPrefix` setting (`cavvy/` unless set); edit it or click **Suggest** again. A name that's taken or isn't a valid branch name is refused before anything is committed.

### Pushing and pull requests

**Push…** beside Commit opens a confirmation dialog for this session's repo or worktree, including clean branches. It shows the remote URL and destination branch, plus ahead/behind counts from local tracking refs (unknown before an upstream exists). A single `origin` is used when there is no upstream; ambiguous remotes need an upstream configured in a terminal. The dialog checks the remote's current default branch. Pushing `main`, `master`, that default branch, or to a remote whose default is unknown needs an extra checkbox. Detached HEADs are refused. Pushes never force, mirror, publish tags or recurse into submodules; this GUI flow disables repository hooks. Rejected updates show Git's output and must be reconciled in a terminal.

With authenticated GitHub CLI (`gh auth status`) and a github.com destination, the dialog offers **Open pull request**, with editable commit-derived title, description, base branch and Draft. The confirmation names the destination and base. It pushes missing commits first, reuses an existing open PR, and redacts outgoing text. **Generate** (only on click) asks the same small model as Generate message for both, from the branch's commits since it left the base in the dialog (or the last commit, when that base isn't found locally), the diff's stat and the diff itself (cut to about 24,000 characters), and the repository's pull request template if it has one (`pull_request_template.md` in the root, `.github/` or `docs/`, any case, or the first file of a `PULL_REQUEST_TEMPLATE/` folder there). What it's shown is redacted. The draft replaces the title and description, with **Undo**; if no model can be used or it fails, a short note says why and the commits' text stays. If `gh` is missing or unauthenticated, **Compare on GitHub** opens a link for github.com remotes; push first to publish new commits. A new pull request opens in the browser once it's made, and its toast offers **Open** too, as a push to a branch that has one does. A PR row in Changes (Branch view) shows its number, title, state, check count and link, and the branch dialog lists it as **Pull request #n** to open. Focus and a 60-second visible-pane timer refresh it; publishing refreshes immediately. Network reads happen only when opening/using the dialog, opening the branch dialog, or refreshing PR state in the visible pane. Only confirmation clicks publish—there is no agent publishing tool. Busy or untrusted sessions cannot publish; repository-owned transport/helper configuration (including worktree configuration and includes) additionally requires explicit user trust. Applicable Git URL rewrites are refused, even in trusted folders: configure a literal remote URL so discovery and push agree. Changed branches or destinations require reopening the dialog, and only the confirmed commit SHA is pushed. PR lookup matches the exact head branch and repository, including numeric branch names. Git and `gh` handle credentials themselves.

## Branches: fetch, pull and switch

A session's title bar shows its folder's branch, with how many commits it is ahead of (↑) and behind (↓) its upstream. The counts come from the remote-tracking branch as it was last fetched, so reading them never touches the network: they're read again when a turn starts or ends, as files change, when you come back to the window, and after a Git action from the app. Nothing fetches in the background; fetching is yours to ask for.

Click the branch (or press Ctrl+Shift+B, ⌘⇧B on a Mac, or **Switch branch…** in the command palette; on Home it acts on Home's folder) to open the branch dialog:

- **Fetch** fetches the branch's upstream remote (or `origin`, or the only remote) and updates the counts.
- **Pull** fetches, then fast-forwards the branch to its upstream, and only that. Up to date, it says so. If both sides have commits it says it diverged and changes nothing: merge or rebase in a terminal (or ask the agent). There's no pull with rebase or merge here, since either can stop half way on a conflict. If uncommitted or untracked files would be overwritten, Git refuses and the dialog names them.
- The list holds local branches, then remote ones not already tracked by a local branch, most recently committed first; typing filters it. Picking a local branch switches to it (`git switch`); picking a remote one switches to its local branch, or makes one tracking it. Git refuses when uncommitted changes would be overwritten, or when the branch is checked out in another worktree, and the dialog says why.
- Typing a name no local branch has offers **Create branch** at the current commit; your uncommitted changes stay as they are.
- With nothing typed, it offers **Create branch** with a name made from the session's title (after the `worktree.branchPrefix` setting), when no branch has it yet.

Switching, pulling and creating are refused while a session works in the folder (a turn, a question, a shell or a task), and hold its sessions while they run. All of it needs a folder you trust: Git runs the repository's configured programs (filters on checkout, for one). Git hooks don't run (`core.hooksPath=/dev/null`), as with worktrees, so a `post-checkout` or `post-merge` hook won't either.

Fetching follows the same rules as publishing: the repository's own transport configuration needs explicit trust, Git runs away from the work tree, a URL rewrite (`insteadOf`) that applies to the remote is refused, it fetches the remote's one URL with the remote's own fetch refspecs (no submodules), and Git and its credential helpers handle credentials. Messages are redacted.

The terminal app has no command for these; use `git` there.

## Working on a pull request

**Work on a pull request…** (in the command palette, and in Home's worktree menu) lists the open pull requests of the folder's GitHub repository, with their author, branch, and whether they're drafts or from a fork. Pick one, or type its number (`#123`) or URL; typing either in the branch dialog offers the same. Cavvy then:

- fetches it from the remote, as **Fetch** does (the same trust and URL rules): a pull request from this repository by its branch, one from a fork by `refs/pull/<n>/head`;
- checks it out in a new worktree in `.claude/worktrees`, as **New worktree…** does (the same trust checks and `WorktreeCreate` hooks): one from this repository on its own branch, tracking the remote's, so ahead/behind, **Pull** and **Push…** work; one from a fork on `pr-<n>`, at its head, with no upstream (pushing to a fork is for a terminal);
- opens a new session there, with `Pull request #123: <title>` and its URL in the message box, for you to say what to do with it.

A fork's pull request is someone else's code, so trusting the repository doesn't trust its worktree: if it has project configuration of its own (`.cavvy/settings.json`, `.mcp.json`, an agent CLI's), its session asks you to trust it first, or to open it without that configuration.

If a worktree is already on that branch, it's opened as it is, without fetching. A local branch of that name that isn't checked out gets a worktree as it is too: update it with **Pull**.

It needs the GitHub CLI, signed in (`gh auth status`). Signed out, the dialog offers **Sign in to GitHub** when a session is open (its sign-in card, see [Signing in](sign-in.md)), and says to run `gh auth login` otherwise. A remote that isn't on github.com is refused: it works only with GitHub for now. A URL of another repository's pull request is refused too.

## Worktrees

Under the new-chat composer, click the branch to select a Git worktree. The menu refreshes each time it opens and shows branches and full paths, including detached worktrees. Selection changes the new chat's folder; existing chats keep their own folders.

**New worktree…** in that menu creates one on a new branch (`git worktree add -b`) and starts the new chat there. The base defaults to the folder's current branch (its commit when detached); the new branch starts at the base's commit and gets no upstream. By default it goes in `<main worktree>/.claude/worktrees/<branch, with / as ->` (where Claude Code keeps its worktrees, even when you start from a linked worktree); you can rename the folder or choose a folder elsewhere. **Suggest a name** asks the project's small model (Settings' small model, else a small model of your default model's provider; Claude Code and Codex need one from another provider) for a branch name from what's in Home's message box, or failing that what's typed in the field, after your `worktree.branchPrefix` setting. Cavvy creates `.claude/worktrees` when it's missing but doesn't touch your `.gitignore`. It refuses an existing branch, an existing path, and a `.claude` or `.claude/worktrees` that is a symlink. Git runs with hooks turned off (`core.hooksPath=/dev/null`), so the repository's `post-checkout` hook never runs; run any setup a hook would have done yourself, or mark a project script as the setup script to have it typed into a terminal tab of each new worktree (see [Project scripts](desktop.md#project-scripts)). Checking files out does still run filter drivers (Git LFS, for example) and anything else Git config sets up for a checkout. Those from your own global or system config always run. In a project you haven't trusted, the repository's own config (`.git/config`) may only hold settings that can't run anything: what `git init` and `clone` write, plus branch and remote bookkeeping. Per-worktree config (`config.worktree`, with `extensions.worktreeConfig`) applies only in its own worktree. Each worktree Git runs in is held to the same rule unless that worktree's own folder (or a folder containing it) is trusted; trusting a sibling worktree doesn't count. When something needs trust, the message names the folder, and the button trusts that folder. Before Git runs in a folder (the one you asked from, and the worktree being removed), Cavvy checks that it really belongs to this repository: its common Git directory must be the main worktree's, and its own Git directory must sit under that one's `worktrees/`. A worktree whose metadata points at another repository (whose config was never checked) is refused outright; trusting wouldn't fix it. If it has anything else (a filter driver, an `include`, `core.sshCommand`, a credential helper, a partial clone's promisor remote, …), you're asked to trust the project first (**Trust and create**), before Git so much as resolves the base. Cavvy's own checks never fetch missing objects in a partial clone (`GIT_NO_LAZY_FETCH=1`); only the checkout itself does, in a trusted project. In a trusted project its filters run as usual.

Worktrees in `.claude/worktrees` also get a remove button. Removal runs `git worktree remove` without `--force`, counting untracked files even if your config hides them, so Git refuses when there are changes. Branches are kept. Git would delete ignored files (an `.env`, `node_modules/`) without asking, so they're listed first, and removal goes ahead only once you've agreed to delete exactly those (**Delete them and remove**). Removal is refused for the main worktree, a locked worktree, and a detached worktree whose commit isn't on any branch. It's also refused while a Cavvy session is open in the worktree: a session in the app counts, including one still closing; a session in another process (such as the terminal) counts once it has sent a message. Git still refuses a worktree with changes, so a session that isn't seen loses nothing. While Git removes it, no session can open in it from the app and no other removal of it starts. Checking for changes reads the files, so it needs the same trust as creating when the repository's own config could run commands (**Trust and remove**). A worktree whose folder is already gone loses only its own record; other worktrees' records stay, even when their folders are away (say, on a drive that isn't mounted).

### An agent working in another worktree

A session follows its agent into another worktree of its repository: the title bar shows that worktree's branch, and the changes chip and review pane read its changes. Going back to the session's own folder switches them back. Where it works is kept with the session, so reopening it, after a restart too, brings it back there, unless the worktree is gone by then.

- Claude Code moves with its own EnterWorktree and ExitWorktree; Cavvy follows the folder it reports at each turn's start and after those tools.
- Cavvy's own models, Codex, OpenCode and Grok Build use Cavvy's EnterWorktree and ExitWorktree. Codex, OpenCode and Grok have none of their own, so they get them through Cavvy's MCP server. EnterWorktree makes a worktree on a new branch, `worktree-<name>`, in `.claude/worktrees/<name>`, as **New worktree…** does (with the project's `WorktreeCreate` hooks), or moves into an existing one. ExitWorktree goes back and keeps the worktree: removing one is yours (above). Both are checked as commands are: Manual and Accept edits ask, Plan refuses them. The agent CLIs call them as `mcp__cavvy__enter_worktree` and `mcp__cavvy__exit_worktree`, and rules naming those (`mcp__cavvy__*` too) apply, though the CLI approves Cavvy's tools itself.
- An agent CLI can't move in the middle of a turn: it's told to work in the worktree by its path until the turn ends. Codex starts its next turn there. OpenCode's and Grok's process starts again there. Both keep a session in the folder it was made in, so each continues in a new session there with the conversation as context, and the transcript says so (after Cavvy restarts, it says the session couldn't be resumed).
- A `cd` into a worktree moves Cavvy's own models too.
- While a session works in a worktree, the worktree counts as the session's folder: removing it is refused (above). Following one in `.claude/worktrees` adds `/.claude/worktrees/` to the main checkout's `.git/info/exclude`, so it doesn't show there as a repository inside it.

## Plans: a new worktree, or a file

When a session presents a plan, its card also offers **New worktree…** (5) and **Save…** (6); the side panel's **Proposed plan** row keeps both (and Copy) once the card is answered, after a reload too. **Implement in a new worktree** creates a managed worktree on a new branch (named from the plan's title; the base is the session's current branch), with the same checks and trust as **New worktree…**, then opens a new session there with the planning session's model, effort and speed, and the plan as its first message (it says where the plan came from and which worktree, branch and base it works in). The new session's mode is one of the Approve choices: by default the mode the planning session was in before it started planning, else your default mode, or Ask for edits if that's Plan. The worktree starts from the base commit, so uncommitted changes don't come along. The planning session's card is answered without approving it: that session stops, still in plan mode, having changed nothing. Both sessions link to each other in the side panel. If the worktree is made but its session can't start (a folder that needs trust, say), the worktree is kept and the dialog says so; starting again uses it. **Save plan** writes Markdown, by default to `~/.cavvy/plans/<project>/<date>-<title>.md` (private, never in the repository); you can pick a file in the project instead. Only files ending in `.md`, inside the session's folder or the Cavvy home, outside `.git/`, through no symlink; an existing file is replaced only after a second, explicit **Replace**.

If model setup fails after creating the worktree and session, the dialog identifies both and offers to open the new session; the original plan remains unanswered.

## Archiving a session in a worktree

Archiving a session whose folder is in a managed worktree asks whether to remove the worktree too (**Archive only** is the default). Removal works as above (no `--force`, ignored files listed first, the branch always kept), and also keeps the worktree when its HEAD has commits no remote-tracking branch contains (in a repository with no remote, that's every commit), when another session (unarchived) works there, and when this session is still working or open in another window or process. The dialog says why before you choose; changes Git refuses are reported when you archive, and the session is archived either way. **Undo** brings the session back but not a removed worktree, and opening a session whose folder is gone says so instead of opening.

## Comparing models

When you're not sure which model will do a task best, give it to two to four at once. On Home, in a Git project, turn on **Compare models** in the model picker and tick the models, from any provider, Claude Code and Codex included. The picker then says how many you picked, and the send button says **Send to N models**. Picking them doesn't change your default model. In a folder that isn't a Git repository the switch is off, with the reason, and a session's own composer is unchanged. Sending creates one worktree per model, one at a time, each on a new branch from the Home folder's last commit, in `<main worktree>/.claude/worktrees/<name>`, the same place and through the same checks as **New worktree…**. Uncommitted changes in the Home folder aren't carried over. It then opens a session in each worktree on exactly that model, with the composer's permission mode and attachments, and sends it the prompt. Each worktree is named after a few words of the prompt and the model, for example `fix-login-redirect-opus-5-5`. Names use only letters, digits and `-`, keys and other secrets are taken out of the prompt first, and `-2`, `-3`, … are added when the branch or folder exists. A sheet then shows each model's result: started, with its branch and folder, or why not and what to do (no key for that provider, a model that isn't listed, images for a model that doesn't take them, a worktree Git couldn't create, …). One model failing never stops the others. A worktree whose session couldn't start is kept, and the sheet names it. A session that can't be set to its model is never sent the prompt, rather than running on the default model. Nothing is deleted for you; remove worktrees as above. In the sidebar a run's sessions stay together under the prompt, in both views, each card naming its model. A session in a run shows the others in its title bar with their status (working, needs you, done, stopped), one click each. Runs are remembered in `gui.json` (the last 50).

Long pasted tasks and attachment-only messages work too (an attachment-only run is labelled “Attached files”); slash-prefixed prompts are sent literally to each model. Text files, PDFs and images use the same attachment checks as ordinary messages; a model that cannot read an attached PDF or image fails only its own row. A separate comparison table is deferred; use the grouped sessions and header switcher to compare replies.

**Cost guard.** Starting more than two models billed per token through an API key asks first, listing them with their prices (or "price unknown"); cancel and nothing is created. Claude Code and Codex run on your plan, and Ollama, LM Studio and other servers on this machine are free, so they don't count. Every other provider does, including Vertex and custom ones. The server enforces this, not only the app.

**Trust for a run.** The Git config rules above apply to every worktree a run creates. When the repository's own config needs trust, nothing is created until you trust the folder it names. Then the run starts again by itself. The new worktrees' project configuration (`.cavvy/`, `.mcp.json`, the agent CLIs' `.claude/` and `.codex/`) is decided once per run, before anything is created. If a folder you trusted contains them (their main worktree, say), they're trusted. If you chose **Open without its configuration** for the Home folder or the main worktree, they open that way too. If they'd have configuration and you haven't decided, the run asks you once (trust the main worktree, or open them without their configuration) and starts after your answer. Nothing is trusted on your behalf. For a linked worktree outside the main folder whose Git configuration needs trust, the run refuses before creating anything: trust the Home folder and main worktree separately, then retry.
