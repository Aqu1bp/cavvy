# Mac apps

With it turned on, agents can use apps on your Mac, each only once you've said yes to it. Four tools (`DesktopControl`, `DesktopSnapshot`, `DesktopAct`, `DesktopScreenshot`) are offered to the models Cavvy runs itself (API models and their sub-agents), and to Claude Code from Cavvy's own MCP server (`mcp__cavvy__desktop_control` and the rest), since it has no computer use of its own. Codex uses the ChatGPT app's computer use where that's set up, and these tools where it isn't ([below](#codex)), never both in one session. The usual loop: the agent asks for an app by name (`DesktopControl action=request_access app=TextEdit`), you're asked "Use TextEdit?", it brings the app to the front (`action=open`), reads it with `DesktopSnapshot`, and acts with `DesktopAct`.

- **Turning it on.** `desktop.enabled` (default `false`; Settings → General → Mac apps). Only your own settings (`~/.cavvy/settings.json`) can turn it on: a project's can't hand your Mac to an agent. Any settings file can turn it off. Off, or not on macOS, the tools aren't offered and cost nothing in a request.
- **Each app is yours to give.** You're asked about every app, in every permission mode: plan and bypass included, past any rule that allows `DesktopControl`, any hook, and auto mode's reviewer. A yes lasts until the session ends (`/clear`, `/resume` or a fork in the terminal app start one; so does Cavvy quitting), and covers that app's windows only. The app is the one macOS knows by that name's bundle id: a copy elsewhere claiming another app's id isn't found. Its sub-agents share the session's apps. Never offered, and refused before you're asked: terminals (Terminal, iTerm2, Ghostty, Warp, WezTerm, Alacritty, kitty and the like), password managers and credential stores (Passwords, Keychain Access, 1Password, Bitwarden and the like), and Cavvy itself, along with the terminal Cavvy runs in. Cavvy's own page in a browser (`cavvy gui`) is never read, clicked or typed into, nor in a screenshot, even in a browser you gave: it's told by its title ("… · Cavvy"). Apps are matched by bundle id once found, and by name before; `NEVER_OFFERED` in `src/desktop/apps.ts` has the list, which the helper also checks itself, whatever it's sent: Cavvy hands it the list when it starts it, right after its secret, and a helper without it refuses every app. Typing into a new document can save it: TextEdit may save one to iCloud Drive as soon as it has text, named from that text, and closing it without saving doesn't undo that. Apps that can run commands themselves are offered (Script Editor, Automator, Shortcuts, a code editor with a terminal, Finder opening a script): giving one gives the agent what it can run there.
- **What reaches only the apps you gave.** Each read and action carries the processes of your apps that are running, and Cavvy's helper checks against the screen as it is, right before each event goes out:
  - a click (or a drag's ends, or a scroll) goes only to a point where the accessibility hit-test finds one of your apps, inside one of its windows (its open menus, and a sandboxed app's Open and Save panels, count as its own). The Apple menu is no app's;
  - a key goes only while one of your apps has keyboard focus: typing is checked before every character. Shortcuts that are the system's (log out, lock the screen, force quit, pictures of the whole screen, moving the keyboard to the menu bar, the Dock or the status menus) and the Apple menu's are refused, judged by the keys that would go out; so are keys while the Apple menu is open, and moving between open menus with the arrows;
  - a screenshot is of your apps' windows on the display with most of them, cut to them, with every other window left out (not covered), at one pixel a point;
  - a snapshot reads one of your apps (the one in front, or one by name).
- **You can always take over.** While Cavvy's helper runs, it watches the Mac's mouse and keyboard (listening only) and tells your input from its own; it won't act when it can't watch. When you move the mouse, click, scroll or type during an action, the action stops at once and its result says you used the Mac, with how much was typed; a click or key that had already gone is done, and a drag goes back to where it started. Between actions, clicking, typing or scrolling in one of the apps you gave makes the next result say so, and a ref from before is refused; what you do elsewhere, answering Cavvy's prompts included, doesn't count (unless Cavvy's page is in a browser you gave: input there counts as using that browser). Esc in Cavvy stops an action too, while Cavvy has focus.
- **Snapshots are text.** An app comes back as an outline from its accessibility tree: its menu bar on one line, an open menu's items, each window with where it is, and in it buttons, text, fields, checkboxes, rows with labels and values, and a ref like `[e12]` on each, standing for the middle of what of it is inside its window. What's scrolled out of its window, scroll bars and a minimized window's contents are left out; what's typed in a password field isn't shown, or said back. Coordinates are screen points from the top left of the main display. At most 3,000 elements are read from an app, and the outline stops at 24,000 characters; both say so.
- **Refs.** A ref is good for one action, which returns a new outline with new refs. Before a ref is used, what it stood for is looked for again: the same kind of element called the same at the same place (a field whose text changed is still the field). If it's gone, or you've used the Mac since the agent last looked, nothing is done and the agent gets the app as it is. (After the helper has stopped for being idle, nothing watched meanwhile: what's there decides alone.)
- **Keys and text.** Text is typed a character at a time as characters, whatever the keyboard layout; a combination (`Meta+S`) presses the key that types that character on the current layout, with Shift when the character needs it. `clear` selects all in the field (`Meta+A`) and deletes it.
- **macOS permissions.** The helper is an app of its own, Cavvy Desktop Control (bundle id `dev.cavvy.desktop.control`), so macOS lists it once. The desktop app carries it (`Cavvy.app/Contents/Helpers`), signed with the app when it's installed (`desktop:install`). With your Apple Development certificate, macOS should keep a grant across new versions (not checked yet). Without the app, or when the app's copy is from another version, it's built with your `swiftc` (Xcode or its command line tools) the first time it's needed, a few seconds, in `~/.cavvy/desktop`, signed ad hoc; an app installed without a certificate is signed ad hoc too. macOS asks about it, not Cavvy or your terminal: it starts by making itself responsible for itself, so the grants are its own, whether Cavvy runs as the desktop app or from a terminal, and Cavvy itself never holds them. A shell command that names the helper, its name or its folder however it's written, asks you every time, in every mode (Claude Code's too: Cavvy hooks its shell tools for it), and auto mode's sandbox can't reach the folder; that's a guard, not a wall, since a command that hides the name isn't caught. The helper takes commands only from the Cavvy that started it, which hands it a secret made for that start over a pipe only the two share: that stops other programs from simply running it, not something already running as you. It needs Accessibility (reading apps, clicks and keys, watching your input; on newer macOS the list is called Device Control and Data Access) and, for screenshots, Screen & System Audio Recording; not Input Monitoring. When one is missing, the desktop app shows a card: "Let Cavvy control apps on this Mac?" for Accessibility (asked when you first give an app, or at the first action), "Let Cavvy take screenshots of apps?" for Screen Recording (at the first screenshot). Its Open Settings asks macOS for the grant, which lists the helper there (macOS may show its own prompt too), and opens that page of System Settings; if the page can't be opened, the card names it. The card then waits for the switch and goes by itself once it's on, and the action carries on. It checks only while it waits: about once a second for Accessibility, which the running helper sees, with a newly started helper every five seconds in case it doesn't; every two seconds for Screen Recording, with a newly started helper, since macOS tells only a process that starts after the grant. Closing the card, stopping the turn, or five minutes without the switch ends it, and the agent is told what to turn on. Without the desktop app (the terminal), Cavvy asks macOS to show its own prompt (once each time the helper starts) and the result says in one line what to turn on, in System Settings → Privacy & Security. If macOS doesn't list the helper, add it with + (Cavvy Desktop Control.app, from where it's kept) and turn it on. Signed ad hoc, a grant is for that build: the same source built again comes out the same (measured: the same code hash), so it lasts until Cavvy changes the helper. After that, macOS still shows the switch on but no longer counts it, and asks nothing (seen on macOS 27.0 with the helper before it was an app): the card offers Reset access, which takes that grant of the helper's out of macOS's list (`tccutil reset Accessibility dev.cavvy.desktop.control`, or `ScreenCapture`; only ever for the helper's own bundle id) and then asks as the first time. Without the desktop app, the result says to remove the entry with −, add it again with + and turn it on. A helper in a temporary folder (a Cavvy built or run under `/tmp`, say) can't be listed: macOS doesn't look up apps there by their bundle id, so System Settings can't find it, + takes nothing, and no switch there turns it on (seen on macOS 27.0).
- **Permissions in Cavvy.** Listing apps, snapshots, screenshots and waiting are reads and never ask. Opening an app and acting ask like other tools that execute. A yes to a click or a key covers that call; allowing for the session allows `DesktopAct` whole, and `DesktopControl(open)` by itself. Plan mode reads, and can ask for an app, but doesn't open, click or type. In auto mode the reviewer decides on actions, never on apps. Rules naming `DesktopAct` or `DesktopControl(open)` apply as usual, rules naming `mcp__cavvy__desktop_act` and the rest apply to Claude Code's calls (and Codex's, on Cavvy's tools) too, and deny rules always win.
- **The helper** starts on the first call and stops a minute after the last one ends; while it isn't running, nothing watches the Mac. One serves every session.
- **A test copy.** To try a change that needs these grants without touching the ones you gave the Cavvy you use, `bun scripts/test-copy.ts build` builds the app as Cavvy Test (`dev.cavvy.desktop.test`) with its helper as Cavvy Desktop Control (Test) (`dev.cavvy.desktop.control.test`), entries of their own in System Settings, and puts it at `~/Applications/Cavvy Test.app`, always there; `bun scripts/test-copy.ts sign` signs it with your Apple Development certificate from your login keychain, named outright (macOS may ask to let `codesign` use the key), so a rebuild at that path keeps the grant. `show` says what it's signed as, `remove` takes it out. Launch it directly with homes of its own (the script's header has the command); they may be under `/tmp`, since the helper is the app's own. Release builds and `desktop:install` keep `dev.cavvy.desktop.control`.

## Codex

Under the same setting and the same rule (each app is yours to give), a Codex session uses one of two ways, for the whole session:

- **The ChatGPT app's computer use**, where it's set up: Computer Use set up in the ChatGPT app, which turns on its `unified-computer-use@openai-bundled` plugin in your Codex configuration and installs its service in `~/.codex/computer-use`, and the session on your default Codex account. Cavvy leaves that setup as it is: it starts nothing of the app's and writes nothing to your Codex configuration. macOS asks about the permissions of ChatGPT's Computer Use, not Cavvy's. Its service serves a Codex that Cavvy starts only when Codex runs with your own `HOME` (measured with Codex 0.169 and ChatGPT 26.1106; `CODEX_HOME` can point elsewhere).
- **Cavvy's tools**, as Claude Code has them, with the same questions, rules and modes, everywhere else: where it isn't set up (its plugin off, or turned on only by a project), on another Codex account added in Cavvy, or once it has failed to start in the session. It doesn't go back to the ChatGPT app's in that session, even once that's set up. Cavvy turns the ChatGPT app's plugin and servers off for the session, as when Mac apps is off.
- **Failing to start.** That's its service not reached (a call's output starts with "… native pipe startup failed", as measured with a `HOME` other than yours) or its server not starting. An app you declined, or code that fails, isn't. Only this is said in the session, once: "ChatGPT's computer use didn't start". The switch takes effect at your next message, not in the turn where it failed. That message starts a new Codex app-server (resuming the thread; after its background work, if any runs). Until then its calls are refused, what it asks is declined, and Codex is told to say so. Where its plugin is off in your configuration, a new app-server also comes at the next message; with another account or no service installed, the first one already has Cavvy's tools.
- **Approvals.** Codex asks for an app when it first needs it, and you're asked "Use Safari?" in every mode, plan and bypass included: no rule, hook, auto mode's reviewer or bypass answers it. Allow once; for this session (Cavvy answers yes for that app until the session ends, unless a deny rule for `DesktopControl` is added meanwhile); or always, which Codex's computer use keeps itself, for later sessions and the ChatGPT app too. A link it asks you to open, to set it up, is cancelled rather than declined, as a decline would be kept as a refusal. **Once an app is allowed, the steps in it don't ask**, in any mode, plan included: its calls (`mcp__cua_repl__js`, the code that reads and operates apps) are marked read-only by ChatGPT's computer use, and Codex doesn't ask about read-only tools. So the app is what you're asked about, not each click or key in it. In bypass Codex runs on-request instead of never: under never, Codex says yes to an app by itself.
- **Apps never offered.** The apps listed above are refused when Codex asks for one, without asking you, and Codex is told so. Cavvy also tells Codex to deny them (`computer_use.macos.bundle_ids`); Codex 0.167 didn't pass that on to the ChatGPT app's service, which is why Cavvy refuses them itself. A call that used one anyway (a yes kept from elsewhere, such as the ChatGPT app's own "Always allow") stops the turn.
- **Off.** With `desktop.enabled` off (turning it off or on mid-session takes effect from the next message), or for a read-only agent, neither is used: Codex's computer use is off in Cavvy's sessions, also where your Codex configuration turns it on: its plugins (`unified-computer-use@openai-bundled`, `computer-use@openai-bundled`) and servers named `cua_repl`, `computer-use` or `node_repl` are turned off for the session. A project's Codex configuration can't turn it on.
- **Commands naming the helper.** Codex runs some commands without asking Cavvy (in auto and bypass), so while Mac apps is on, or once the helper has been built, Cavvy adds its PreToolUse hook to Codex, which Codex runs before every tool call in every mode: a shell command naming the helper asks you there, every time, as above, and only once even where Codex then asks too. So does a call of Codex's computer use whose code names it, in that hook (Codex doesn't ask about those calls itself); code it loads from a file, or a name it puts together, isn't seen. Each tool call then makes one round trip to Cavvy. A Codex without hooks (before 0.160) asks about every command in bypass instead; in auto it isn't guarded.
- **In the transcript.** A call shows what it does, then in which app once Codex says: "TextEdit: Type the note".
- **What was measured** (Codex 0.167, ChatGPT 26.1106). Codex passes each app approval on from its computer use (an MCP elicitation from `cua_repl` naming the app's bundle id), and says which app a call used in its result. It doesn't pass `computer_use.macos.bundle_ids` on, and asks about an app it denies all the same, which is why Cavvy refuses those apps itself. `features.computer_use=false` doesn't turn computer use off; turning its plugin off does. With Codex 0.169, its `js` and `js_reset` tools say they're read-only, so Codex runs them without asking in every mode; Cavvy's PreToolUse hook still runs before each.
