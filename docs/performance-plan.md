# Performance goal

Cavvy is a light wrapper over the agents it runs: under heavy use the hardware runs out, not the app. So each target below is measured against what the same work costs without Cavvy (the same CLIs run bare, in terminals), on the same machine and in the same run, not against a fixed number. A target is met when it holds in two runs in a row under the whole workload below, not just with one or two sessions. One that turns out to be out of reach (Electron's own floor, say) stays listed with the measured reason; it isn't lowered.

## The heavy-use workload

Every target must hold under all of this at once. Where it can't run on a real 16 GB laptop, it runs in a 16 GB cgroup.

- 30 sessions open, 10 streaming at the same time
- spread across many worktrees of large repositories (100,000 files, over 1 GB)
- sessions 2,000+ turns long, tool output of tens of MB, many images
- agents running builds, test suites, dev servers and file watchers
- subagents, background tasks and MCP servers in many sessions at once
- 1,000 sessions in history; the app left open for a week (a long soak stands in for this)
- bursts: many sessions finishing at once, rate limits hitting all of them together

## How it's measured

`scripts/bench-ramp.ts` runs N real Claude Code sessions, each in its own worktree of a large repository (`scripts/bench-repo.ts`), given the same prompts (an edit and a build, a subagent's search, megabytes of tool output, a dev server, a commit), either under one `cavvy serve` as the desktop app runs it or as bare `claude -p` processes. Each session sends its next prompt as soon as its last turn ends. With a fixed number of turns each, it reports the wall time to the last turn's end and the whole machine's CPU over it, which is what the same work cost; every second, CPU and memory by role (Cavvy, its own helper processes, the CLIs, what the agents run), the machine's pressure, turn times and failures, and how fast Cavvy's socket answers; and, with the kernel's process accounting, every process's CPU, short-lived ones too, by command and role. Sampling processes once a second misses most of what agents run (a git or a compiler lasts a fraction of a second), and a clock that counts samples rather than time reads short on a busy machine: both made an earlier version of this bench say Cavvy was faster than the bare CLIs when it wasn't. Real models are the evidence. Where a comparison has to be exact (the same work to the byte in both), a stand-in for the model's API scripts the replies, and the CLIs and everything they run are real.

The Mac-only targets (5, 7, and the window's share of 3 and 9) are measured with the packaged app: `bun run perf:bench`, `desktop-electron/bench-heavy.ts` and `bench-real.ts`, by instruction counts, not milliseconds:

- **Instructions and energy decide.** A build that does less can show the same milliseconds or more, because macOS moves lighter work to slower cores: during a reply only 8–14% of the work runs on performance cores. Milliseconds still say how something feels, but they aren't a fair comparison between builds or between machines.
- **A figure that looks too good is suspect.** A bench must fail if it isn't measuring what it says: `bench-stream` stops if a session didn't open, because the rail holds its rows while the real cursor is over it, and a stretch on the wrong session reads as a great result. Bench connections call `session.shown`, or the server counts them as looking at everything.
- **Tracing inflates.** Rows from `bench-reply`'s trace run slower than the same work untraced.

## Long sessions

A session's files are append-only logs: its transcript (`~/.cavvy/projects/<project>/<session>.jsonl`) and, for a CLI's turns, the steps the window showed (`ui/<session>.jsonl`). Building its turns from them reads all of both, so a long session cost more to open the longer it got. Now:

- The window is sent the last turns that fit in 64 KB (at most 100) and asks for earlier ones as you scroll up. Find searches the turns it hasn't been sent on the server.
- As a session with more than 20 turns is let go of, its turns and sub-agents are written to its turn store (`turns/<session>.jsonl`, with an index in `turns/<session>.json`). Opened again, it reads the index and its latest 20 turns from there; any other turn is read when it's sent. A notice shown only while the session was open (a model that isn't available, say) isn't kept, as building the turns again wouldn't show it.
- The store is used only if both logs are byte for byte as they were when it was written. A session written to elsewhere since (a terminal, another copy of Cavvy), or one that crashed, is built from its logs again. Deleting a session moves its store to the trash with its other files.
- What a turn is sent with leaves out what its rows don't show until they're opened. A finished turn's work comes folded: each call's name, status and summary, not its output or diff (the turn comes whole as its work is opened or found in), unless Settings → Expand tool activity is on. Its thoughts come without their text, fetched as a row is pointed at or opened. An edit's change comes once, in its diff. Finished sub-agents of turns not sent are counted, and the Agents list's Finished fold fetches them as it's shown.
- Find works through turns the window hasn't been sent in slices of 8 ms, so other sessions keep streaming meanwhile. What it searches in each turn is kept for the next query and let go of 2 minutes after Find was last used: 30 MB for a 100,000-item session.
- Opened for the first time (or after its logs changed), a session's turns are sent first and stored after, 8 ms at a time, a new turn meanwhile included.
- A rewind builds again only the turns since the last compaction (it can't reach past one); those before stay as they are.
- Back at the end of a session for 5 s after reading far up, with nothing coming, the window draws its first page again and keeps only those turns; scrolling up brings the rest back as "Show earlier" does.
- A remote window's SSH tunnel is compressed: a reply's messages are mostly the same few ids each time.
- A window back after its connection dropped asks for all the sessions it had open at once, with the lists, each with what it had: a session that still has every message sent since (it keeps the last 64 KB of them) sends only those, and the window carries on where it was. Otherwise, or after the server started again, it's sent the session's last turns, as when it's opened (up to 64 KB each, one after another before).
- A transcript read more than 1 MB past its last checkpoint gets a new one (`state/<session>.json`): what reading it came to, and how far it read. Next time only what's after is read, if the file still ends there as it did. Kept only when it's under half what it replaces, so a session never compacted gets none.

Not yet:

- A Claude Code session's transcript (never compacted here) is still read whole as it opens, and its whole history kept in memory: 6 MB at 30,000 items (Linux), 16-20 MB at 100,000 (M5). Loading it as it's needed wouldn't hold: while a session runs, the agent reads all of it (estimating its context, listing rewind and fork targets, the CLI's context from where it was synced), from 103 places.
- Bytes on the wire per character of a reply streamed to a remote window: 1.5 through the compressed tunnel, at about Opus's pace (target 1.2). The text is 0.26 of it, flushing a message for each chunk the model sends 0.56, and the message around it 0.71 (mostly its sequence number). Fewer messages means sending text less often than every 24 ms, which made a reply feel worse. A smaller message doesn't get there: a run of appends to one block sent with only its session, sequence number and text came to 1.47, and without the sequence number (which keeps them in order) 1.27.
- Palette search: 19-27 ms a keystroke with 10,000 sessions (Linux), most of it a stat of every session file, so that what another process just wrote is found. Watching the folders instead (inotify, on Linux) isn't enough: under load its events came after the search that needed them, so a session just written was missed.
- Find jumping far back loads every turn between.
- Opened for the first time, or after its logs were written to elsewhere (a CLI in a terminal, a crash): built from its logs. A compacted session of Cavvy's own models has its last segment's turns built and sent first, and the earlier ones built after, a segment a slice, before it's stored (what's asked of them waits for them): 217-229 ms for a 100,000-item one (it was 566-580 ms, Linux). A Claude Code session (one segment) is built at once: 1.1-1.3 s (Linux; 465-670 ms on an M5). Opened after the server started again, from its store: 14-21 ms and 83-92 ms, most of the Claude Code one reading its transcript (9.6 MB, 52 ms).
- Work done in slices (Find, the turn store, those earlier turns) takes turns: one slice a turn of the event loop (`src/util/slices.ts`). Two resumed together ran one after the other, and held the server 21-23 ms.
- Opened for the first time, every turn is built before it's stored: at 100,000 items, 135 MB (Cavvy's own models) and 294 MB (Claude Code) in the server just after the window is sent its turns, 15 and 61 MB once they're stored, a second or so later (Linux). Storing them as they're built would put about a second of writing into that first open.

`test/perf-size.test.ts` checks these at 3,000 and 30,000 items. On a Linux container, opening a 30,000-item session again: a Claude Code session in 28 ms, reading 4.7 MB and keeping 6.7 MB in the server; built from its logs, 521 ms and 58.6 MB read (and 132 MB kept, before the store). A session of one of Cavvy's own models: 43 ms and 2.9 MB kept; built, 327 ms.

## Big repositories

@-mention completion in a repository with a listing of 2 MB or more (about 50,000 files) is indexed and searched on worker threads (up to four, leaving two cores), each with a part of the paths, so the server's own thread never scores them. Each keeps its paths as bytes and finds a query in all of them with the engine's own search; one and two characters (the first keystrokes after "@") are answered from what indexing worked out. `scripts/mention-bench.ts`, a million files on a 4-core Linux container with 2 workers: a keystroke takes 1-4 ms at the median and 35-42 ms at most, against 70-180 ms for most queries on the server's thread before. Indexing takes about 2.5 s, on the workers. Their memory is about what the index took on the server's thread: 228 MB for a million files once settled (3 workers), near 400 MB for a few seconds as they index.

Not yet: while they index, the server's thread still stops for up to 6-10 ms once or twice in the 2 s (it was 50-70 ms when it indexed them itself, and 6-7 times as they made a string of each path). It does nothing then: a full collection in a worker stops it too (checked: two workers collecting in a loop held it up to 12 ms; two allocating typed arrays, or computing, didn't). They index from git's listing as bytes now, with next to nothing to collect after. Indexing without working out each character's and each pair's best paths stops it rarely; with it, once or twice. Making that pass allocate nothing for each path (typed arrays in place of small objects and arrays) didn't change it, so what stops the server's thread then isn't known yet.

## Recovery

Not a speed line, but required: if the window's page crashes, it's back in about 150–200 ms with the same session, the reply still coming, the half-written message and the terminal (30 checks in the packaged app: mid-reply, idle, with a browser tab open, hidden, a crash loop). A rule in `test/perf-rules.test.ts` keeps the handler in place.
