# Project files

| File | Purpose |
|---|---|
| `CAVVY.md` (also reads `AGENTS.md`, `CLAUDE.md`) | Notes loaded into every session. `/init` writes one. |
| `CAVVY.local.md` | Personal notes, git-ignored. |
| `~/.cavvy/CAVVY.md` | Notes for all projects. |
| `~/.claude/CLAUDE.md`, `~/.claude/rules/**/*.md`, `~/.codex/AGENTS.override.md` or `AGENTS.md` | Your Claude Code and Codex notes for all projects, so API sessions follow them too (Claude Code and Codex sessions read their own). Rules with `paths:` frontmatter are left out. Loaded before `~/.cavvy/CAVVY.md`, then the project's files. |
| `.cavvy/settings.json`, `.cavvy/settings.local.json`, `~/.cavvy/settings.json` | Settings: project, personal, user. |
| `.mcp.json` | Shared MCP servers; Cavvy approvals are bound to what each server runs by a fingerprint saved in local settings (`/mcp` to review and approve). Legacy name-only approvals ask again. In user-trusted folders, Claude Code reads the file itself; Cavvy enables only project servers its manager permits starting whose raw definitions still match the approved snapshot and use only fields the approval covers, and disables all others (a definition Claude Code would read differently isn't passed on: one with `headersHelper` or `oauth`, `${VAR}` expansion, a `type` that doesn't match a single command or URL, or a `cwd` other than the project folder). |
| `.cavvy/agents/*.md`, `~/.cavvy/agents/*.md` | Custom sub-agents (frontmatter: `name`, `description`, `tools`, `model`). |

Settings files may contain `//` and `/* */` comments and trailing commas. A settings, credentials, providers or trust file that has a JSON error is ignored (with a warning) and is never overwritten: saving a setting into it fails with a message naming the file, so nothing in it is lost. Saving rewrites the file as plain JSON, so comments in a file Cavvy edits are not kept.

## Trust and memory files

When a folder contains Cavvy configuration, you're asked once whether you trust it. Until you do, its settings, hooks, MCP servers, commands and memory files (CAVVY.md, AGENTS.md, CLAUDE.md) are ignored, except deny/ask rules, which only add restrictions. Memory files are only read when they are markdown inside the project (a symlink pointing elsewhere is skipped). `@path` in any memory file imports another file, as in Claude Code: relative to the importing file (or `~/...`, or absolute), up to four hops deep; a missing one is skipped. An imported file comes before the file importing it. What's code is what a CommonMark parser (Bun's) reads as code: `@path` inside a code span, a fenced or indented code block (in block quotes and list items too), an HTML block or an HTML comment isn't an import. The path itself is taken as written: Markdown's emphasis, entities and links don't change it (`@docs/_draft_.md` is `docs/_draft_.md`), and `\@path` or `&#64;path` isn't an import. A project's memory files import only from inside the project until you trust the folder yourself: a folder trusted only because it had nothing to protect doesn't count, as Claude Code asks before it loads such external imports. A memory file that imports from outside the project therefore counts as configuration, and the trust question names those imports; a run's new worktrees are checked as committed, so a committed import the working copy has since dropped still asks first. Your own files (`~/.claude`, `~/.codex`, `~/.cavvy`) may import from anywhere. Only markdown is imported, so `@.env`, `@~/.aws/credentials` or `@~/.cavvy/providers.json` stay literal text. Nothing under `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.azure`, `~/.kube`, `~/.docker`, `~/.config/gcloud` or `~/.password-store` is read even when it is markdown, whether reached through a symlink (or with those folders themselves symlinked) or spelled in another case. Each memory file is capped at 40 KB, and all of them together at 200 files and 200 KB. Files count as they're read: yours, then the project's from its root down, each followed by what it imports, nearest imports first; files past the cap are left out, and the prompt and `/memory` say which. The rules folder walk stops after 100 folders, 2,000 entries or 8 levels; a folder with more entries than the walk has left is left out whole, with a notice, rather than cut wherever the system happens to list it. Branch-only callers such as project inspection and initial session state still read only branch metadata, with `core.fsmonitor` disabled. Git prompt context includes recent commits without signature verification or lazy fetching. Before explicit user trust, it also reads status when the repository’s local and worktree configuration (including includes) has no filter, fsmonitor, submodule or hook execution settings; status ignores submodules. Otherwise it skips status and names the configuration section or check failure in the prompt, without values. User-trusted folders retain status regardless of those settings. Creating a worktree also turns hooks off, and needs trust when the repository's own config could run commands on checkout; see [Worktrees](git.md#worktrees).
