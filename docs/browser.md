# Browser

Agents can open web pages, to check the UI they build. Six tools (`BrowserNavigate`, `BrowserSnapshot`, `BrowserAct`, `BrowserScreenshot`, `BrowserEval`, `BrowserLogs`) drive a headless Chrome, Chromium, Edge or Brave over the DevTools protocol, with nothing to install but the browser itself; they're offered when one is found. API models get them as built-in tools; Claude Code and Codex get the same tools from Cavvy's own MCP server (`mcp__cavvy__browser_navigate` and the rest), and screenshots reach them as images. The usual loop: start the dev server in the background, `BrowserNavigate` to `http://localhost:PORT`, read the page with `BrowserSnapshot`, and act with `BrowserAct`.

- **Snapshots are text.** A page comes back as an indented outline from its accessibility tree: roles, names, values and states (checked, disabled, expanded), link targets, and a ref like `[e12]` on everything to act on. Password values are never shown, and the outline stops at about 24,000 characters (it says so). Refs last until the page navigates; an old one is refused with a note to snapshot again. `BrowserAct` clicks and types with real mouse and key events, scrolling the element into view first, and answers with what changed in the outline. A screenshot is an image, only when asked for. Console messages, uncaught exceptions and requests (method, URL, status, failure; no bodies) are kept per tab, newest 200 and 300, with secrets redacted.
- **Where it may go.** `http:` and `https:` pages, `about:blank` and files inside the project. `javascript:`, `data:`, `chrome:`, `view-source:`, `blob:` and files outside the project are refused, also when a page redirects or scripts its way there. Downloads are refused and noted in the logs. What a page does on its own is held to the same rules, in its frames too (those from other sites included): a redirect, link or script that would take it to a host a `WebFetch(domain:…)` deny rule names, or to a file a `Read` deny or ask rule covers, is blocked and the console says why. So is one to a host an ask rule names, except the host the agent was let open in that tab (or you went to), while the tab stays there: a page can't take the agent somewhere it would be asked about, as `WebFetch` doesn't follow a redirect to another host; opening a file with `BrowserNavigate` follows the `Read` rules (deny and ask rules, the credential store, files that may hold credentials), and an approved file load grants only that exact file for that navigation. A page opened from a file can't load others from outside the project. A JavaScript `alert` is accepted and logged; a `confirm` or `prompt` waits for the agent to answer it (`BrowserAct action=dialog`).
- **Permissions.** Reading (snapshot, screenshot, logs) is read-only and never asks. Opening `localhost`, `127.0.0.1`, a file or a blank page is allowed; opening any other host asks like `WebFetch`, and `WebFetch(domain:example.com)` rules cover it. Clicking, typing and `BrowserEval` run a page's own scripts and can submit its forms, so they ask like other execute-level tools ("don't ask again" allows the tool in the project), and a yes covers that call alone: the same click or script on the next page asks again; hovering, scrolling and waiting don't. Plan mode allows opening, reading and scrolling, not acting (hovering included, since a page's hover handlers run). Hooks run for these tools as for any other. Claude Code and Codex call them as `mcp__cavvy__browser_navigate` and so on, and rules naming those (`mcp__cavvy__*`, `mcp__cavvy__browser_act`) apply too, though the CLI approves Cavvy's tools itself.
- **One browser per project, a profile of its own.** Chrome starts with the first page, with a profile under `~/.cavvy/projects/<project>/browser` that keeps logins and cookies between runs, and ends with the last session using it, after 10 minutes unused, or with Cavvy (on Windows, a Cavvy killed outright, from Task Manager say, leaves its browser running; elsewhere a watcher stops it). It's driven over a pipe only Cavvy holds (on Windows, over a port on 127.0.0.1, which other programs on the machine can reach). Each session has its own tabs (at most 8), closed with it. Tabs use separate Chrome windows so different sessions can stream concurrently. If Chrome dies, the tool call says so, and the next page starts a new one. The terminal UI and `-p` runs use it too.
- **In the GUI,** the side panel's **Browser** tab shows the session's current tab (streamed as frames, only while the tab is showing) with an address bar, back, forward, reload and the tab strip, and the page takes the pane's size. A dot on the tab and a toast say when the agent opens a page. You can click, type and scroll in the page while the agent works in it, as in T3 Code: neither keeps the other out. The next time the agent reads the page it's told you used the tab, alongside what changed since it last looked, so it doesn't mistake your changes for the page's. Where you take the page (a link you click, a sign-in redirect) is yours to go, as an address you type is; once the agent acts again, its own rules apply. Pasted text and committed IME compositions arrive as text; `Shift+Esc` leaves the page for the address bar. It works in the desktop app and in `cavvy gui` in a browser, since Chrome runs next to the server. Clipboard copy out of the page isn't supported.
- **In the desktop app** the browser is the app's own Chromium, not a headless Chrome: each tab is a real page in the window, which you use directly (scrolling, selecting and copying, IME, as in any browser), and the agent drives the same tabs over the app's connection to the server, which opens no DevTools port. Each project keeps its own cookies and storage. A tab nobody sees and nobody has used for 30 seconds sleeps (it isn't drawn, and costs next to no CPU) and wakes when a pane shows it or the agent uses it. A popup you open (a site's sign-in window) is a window of its own that keeps `window.opener`, so the page it reports back to gets the answer; it goes only to web pages and closes with its tab. A popup the agent opens is a tab. No Chrome is needed; `cavvy gui` in a browser still uses one, streamed as above.
- **Find, sizes, zoom and DevTools.** The pane's **⋯** menu has:
  - **Find in page** (also `Ctrl+F`, or `⌘F` on a Mac, while the keyboard is in the pane or its page). It shows "3 of 12"; `Enter` and `Shift+Enter` go to the next and previous match, and `Esc` closes the bar and clears what it marked. In the desktop app this is Chromium's own find. On a headless Chrome a script searches the text that shows, in a world of the pane's own in the page (the page's scripts neither see it nor change what it finds). It marks the matches with CSS highlights, which change nothing in the page's DOM, and it finds up to 1,000. It runs only when you search, and the agent isn't told of it.
  - **A size**: Fill pane (the default), Phone 390 × 844, Tablet 820 × 1180, Laptop 1280 × 800, or a custom one. The page takes that size and is drawn scaled down to fit the pane, never larger than it is; a bar under the tabs lets you type the width and height, rotate, zoom, or go back to filling the pane. Only the size changes, as in a desktop browser's narrow window: the user agent stays a desktop one and there's no touch. While the pane shows the page at that size, that's the size the agent's screenshots see too. Once nobody watches, a headless page goes back to the agent's 1280 × 800; a desktop-app page goes back to its usual size when the pane stops showing it. The size is kept for each session while the window is open.
  - **Zoom** in, out and back to 100%, as a browser zooms. On a headless Chrome that's the page given fewer CSS pixels across, each drawn larger, so it stays sharp. In the desktop app it's Chromium's zoom, put back to 100% for the agent when the pane stops showing that tab.
  - **Open DevTools**, in the desktop app only: Chromium's DevTools for that page alone, in a window titled "DevTools: " and the page's title. It opens where you last left one, or beside the app's window on the same display (right of it, else left), at the window's height; with no room beside it, over the side of the window away from the Browser pane. Choosing it again brings that tab's window to the front, and it closes with its tab. The agent goes on driving the page while they're open. Not offered with a headless Chrome, which is driven over a pipe and opens no DevTools port. Opening one for a frontend to reach would let any program on the machine drive a browser that holds your logins.
  None of these sends the page anything until you use it: a pane that fills and isn't searched asks for the same pictures as before.
- **Display quality.** The pane uses a dedicated authenticated binary stream and a Retina Chrome compositor, at one size and quality whether the page is still or moving. Wheel turns go to Chrome as they happen, and transport and decoding each keep only the newest waiting picture. Taking the tab or a page's dialog never resizes the page. Stream reconnects leave chat connected, and disconnected viewers release held keys and mouse buttons. `scripts/browser-perf.ts` measures input-to-picture latency and frame rates against a real Chrome.
- **Sites see Chrome.** The headless browser tells sites it's the same Chrome with a window (user agent and client hints, `navigator.webdriver` false), so Google, YouTube and the like don't answer it with a robot check.
- **Settings.** `browser.enabled` (default `true`; Settings → General → Browser; any settings file can turn it off). `browser.executable` names a browser to run instead of the one found, and `browser.headless: false` shows its window while you debug; both count only from your user settings, since a project must not choose what gets launched. The `CAVVY_BROWSER` environment variable names a browser too, and wins. Without any browser, the tools aren't offered and the pane says how to fix that.
